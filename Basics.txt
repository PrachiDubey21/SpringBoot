HTTP->
HTTP (HyperText Transfer Protocol) is a communication protocol used to 
transfer information between a client and a server over the internet. 
When we open a website, the browser acts as the client and sends an HTTP 
request to the server. The server processes the request and sends an HTTP 
response back to the browser. HTTP is not encrypted, which means the data being 
transferred can potentially be intercepted and read by an attacker. 
Therefore, HTTP is not considered secure for sensitive information such 
as passwords, banking details, or personal data.

It tells request / response structure , how data will be send
by default (non encrypted)
--> GET , POST , DELETE , PUT , PATCH  (calls)



HTTPS->
HTTPS (HyperText Transfer Protocol Secure) is the secure version of HTTP. 
It is used for communication between a client and a server while protecting 
the data through encryption using TLS (Transport Layer Security). 
When a user sends sensitive information through an HTTPS connection, 
the data is encrypted before being transmitted, making it much harder for 
attackers to read or modify. Websites using HTTPS generally have a URL 
beginning with https:// and display a lock symbol in the browser.

(encrypted)

Spring Framework

Spring Framework is an open-source framework for developing Java applications. 
It provides a set of tools and features that make it easier to build large, 
flexible, and maintainable applications. One of its main features is 
Dependency Injection (DI), where Spring manages the creation and dependencies 
of objects instead of the programmer creating them manually. 
Spring also provides features for developing web applications, 
working with databases, handling transactions, security, and more.

The Spring Framework is based mainly on the concept of IoC (Inversion of Control), 
which means that the control of creating and managing objects is given to the 
Spring container. Objects managed by Spring are called Spring Beans. 
Spring is modular, so developers can use only the features they need.

In simple words, Spring Framework makes Java application development easier 
by managing objects, reducing tightly coupled code, and providing ready-made 
features for common application requirements.

Spring Framework vs Spring Boot -->
Spring Framework is the main framework that provides features such as 
Dependency Injection, IoC, database support, web development, and security. 
Spring Boot is built on top of Spring Framework and makes Spring application 
development easier by providing auto-configuration, starter dependencies, 
and embedded servers, so much less configuration is required.

                             MAVEN LIFECYCLE

Definition
Maven Lifecycle is a predefined sequence of steps that Maven 
follows to build and manage a Java project. It defines the different 
stages of the build process, such as validation, compilation, testing, 
packaging, installation, and deployment.

Maven has three standard lifecycles: Clean, Default, and Site.


1. Clean Lifecycle
The Clean Lifecycle is used to clean the project by removing 
files generated during previous builds.

The main phases are:
pre-clean → clean → post-clean

The most commonly used command is:
mvn clean

In our project, we can use:
.\mvnw.cmd clean

The clean phase generally removes the target directory.



2. Default Lifecycl
The Default Lifecycle is the main lifecycle used for building a Maven project.

Important phases are:

validate
   ↓
compile
   ↓
test
   ↓
package
   ↓ 
verify
   ↓
install
   ↓
deploy

Validate -> The validate phase checks whether the project is correctly 
configured and ready for the build process.
mvn validate

Compile -> The compile phase compiles the Java source code into .class files. 
.java files → .class files
mvn compile

Test -> The test phase runs the tests written for the project.
mvn test

Package -> The package phase packages the compiled application 
into a distributable format such as a JAR.
mvn package
For a Spring Boot application, the JAR is generally created 
inside the target folder.

Verify -> The verify phase performs additional checks to verify 
that the project meets the required conditions.
mvn verify

Install -> The install phase installs the packaged project 
into the developer's local Maven repository.
mvn install
The local Maven repository is generally located at:

C:\Users\<username>\.m2\repository

Deploy -> The deploy phase uploads the packaged project 
to a remote Maven repository so that it can be shared with other 
developers or projects.
mvn deploy


3. Site Lifecycle

The Site Lifecycle is used to generate documentation and reports 
for a Maven project.

Its main phases are:
pre-site → site → post-site → site-deploy

It is mainly concerned with project documentation rather than 
building the application.

Important Rule -> 
Maven executes the phases that come before the phase you specify.

For example, if you run:
mvn package

Maven performs:

validate
   ↓
compile
   ↓
test
   ↓
package

If you run:
mvn install

Maven performs the required earlier phases and then install.

Therefore: A later Maven phase automatically includes the 
required earlier phases.

.\mvnw.cmd spring-boot:run

spring-boot:run is not a Maven lifecycle phase. It is a goal 
provided by the Spring Boot Maven Plugin.

So:

while:

→ spring-boot:run

Dependency Injection means Spring creates the objects you need and 
provides them to your class instead of you creating those objects yourself.

Dependency Injection (DI) is a design pattern in which the objects required 
by a class are provided to it from outside instead of the class creating them 
itself. In Spring Boot, the Spring IoC container creates and manages these 
objects, called beans, and provides them to the classes that need them. 
This reduces tight coupling between classes and makes the application easier 
to maintain and test. For example, if a UserController needs a UserService, 
we don't create the UserService using new UserService(). Instead, Spring 
creates the UserService bean and injects it into the UserController. 
Dependency Injection can be done mainly through constructor injection, 
setter injection, and field injection.

Inversion of Control (IoC)

Inversion of Control (IoC) is a principle in which the control of creating, 
configuring, and managing objects is transferred from the programmer to the 
Spring Framework. Normally, we create objects ourselves using the new keyword. 
In Spring, the IoC Container takes responsibility for creating and managing 
these objects, which are called Beans.



Without IoC
Normally, the programmer creates and manages objects:

Programmer
    ↓
creates object using new
    ↓
Object is created
    ↓
Programmer manages the object
    ↓
Class uses the object

Example:
Engine engine = new Engine();
Car car = new Car(engine);

Here, our code controls object creation.



With IoC
In Spring, the control is given to Spring:

              Spring Framework
                     ↓
              IoC Container
                     ↓
          creates and manages objects
                     ↓
                  Beans
                     ↓
       provides required objects
                     ↓
              Application Classes

So instead of our code creating everything, Spring manages the objects for us.

Example:

@Component
class Engine {
}

Spring sees @Component and creates an Engine object and manages it as a Bean.

If another class needs Engine:

@Component
class Car {

    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }
}

The flow is:

Engine class
    ↓
@Component
    ↓
Spring IoC Container
    ↓
creates Engine Bean
    ↓
Car needs Engine
    ↓
Spring provides Engine to Car

Why is Constructor Injection Recommended?
Dependencies are mandatory — The object cannot be created without its 
required dependencies.

Supports final fields — Dependencies can be declared as final, 
making them safer and immutable.

Easy to test — Dependencies can be directly passed through 
the constructor during unit testing.

Clear dependencies — The constructor clearly shows what dependencies 
the class needs.

Prevents NullPointerException — Required dependencies are provided when 
the object is created.

Less Spring-specific code — You don't need @Autowired when the 
class has only one constructor.

Better maintainability — The class's dependencies are explicit and 
easier to understand.

Steps of ApplicationContext in Spring

1) Create the Spring container
ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

2) Spring reads the configuration
It reads @Configuration, @ComponentScan, @Bean, etc.

3) Spring scans for components
It finds classes marked with @Component, @Service, @Repository, @Controller, etc.

4) Spring creates the beans
Objects of these classes are created and managed by the Spring container.

5) Spring performs Dependency Injection
Dependencies are automatically provided using constructor injection, 
@Autowired, etc.

6) ApplicationContext stores and manages the beans
You can get a bean from the container:
StudentService service = context.getBean(StudentService.class);

7) Application uses the beans
You use the objects provided by Spring instead of creating them manually.

# HTTP Status Codes

HTTP status codes are 3-digit numbers sent by the server to 
indicate the result of an HTTP request. 
They are divided into five categories: 1xx, 2xx, 3xx, 4xx, and 5xx.

## 1. 1xx – Informational Responses

The request has been received, and the server is continuing the process.

* **100 Continue:** Client can continue sending the request.
* **101 Switching Protocols:** Server agrees to switch protocols.
* **102 Processing:** Server is processing the request.
* **103 Early Hints:** Server sends preliminary information before the final response.

## 2. 2xx – Success Responses

The request was successfully received and processed.

* **200 OK:** Request completed successfully.
* **201 Created:** A new resource was created successfully.
* **202 Accepted:** Request was accepted for processing but may not be completed yet.
* **204 No Content:** Request succeeded, but no response body is returned.
* **206 Partial Content:** Only part of a resource was returned.

## 3. 3xx – Redirection Responses

Further action is required, usually to access a resource at another URL.

* **301 Moved Permanently:** Resource has permanently moved to another URL.
* **302 Found:** Resource is temporarily available at another URL.
* **303 See Other:** Client should retrieve another URL, generally using GET.
* **304 Not Modified:** Resource has not changed, so a cached copy can be used.
* **307 Temporary Redirect:** Temporary redirection that preserves the HTTP method.
* **308 Permanent Redirect:** Permanent redirection that preserves the HTTP method.

## 4. 4xx – Client Error Responses

The request has a problem or the client does not have permission to access the resource.

* **400 Bad Request:** Request is invalid or malformed.
* **401 Unauthorized:** Authentication is required or has failed.
* **403 Forbidden:** Client does not have permission to access the resource.
* **404 Not Found:** Requested resource or endpoint was not found.
* **405 Method Not Allowed:** HTTP method is not supported for that endpoint.
* **406 Not Acceptable:** Server cannot provide an acceptable response format.
* **408 Request Timeout:** Server timed out waiting for the request.
* **409 Conflict:** Request conflicts with the current state of the resource.
* **415 Unsupported Media Type:** Request content type is not supported.
* **422 Unprocessable Content:** Request is understood but cannot be processed due to its content.
* **429 Too Many Requests:** Client has sent too many requests in a given period.

## 5. 5xx – Server Error Responses

The server failed to fulfill a valid request.

* **500 Internal Server Error:** An unexpected error occurred on the server.
* **501 Not Implemented:** Server does not support the required functionality.
* **502 Bad Gateway:** Gateway received an invalid response from an upstream server.
* **503 Service Unavailable:** Server is temporarily unable to handle requests.
* **504 Gateway Timeout:** Gateway did not receive a timely response from an upstream server.

## Important HTTP Status Codes in Spring Boot

* **200 OK:** Data fetched successfully.
* **201 Created:** Student or other resource created successfully.
* **204 No Content:** Operation succeeded without a response body.
* **400 Bad Request:** Invalid input or validation failure.
* **401 Unauthorized:** Authentication is missing or invalid.
* **403 Forbidden:** User lacks the required permission.
* **404 Not Found:** Requested endpoint or resource does not exist.
* **405 Method Not Allowed:** HTTP method is not supported by the endpoint.
* **409 Conflict:** Request conflicts with existing resource state.
* **500 Internal Server Error:** Unexpected application error.



* **1xx:** Informational
* **2xx:** Success
* **3xx:** Redirection
* **4xx:** Client error
* **5xx:** Server error

**Note:** 401 relates to authentication, whereas 403 relates to permission. 
In Spring Boot, `ResponseEntity` can be used to return the appropriate 
HTTP status code from a controller.

In Spring Boot, default exception handling means Spring Boot automatically

Lifecycle of a Filter

1. Instantiation: The servlet container creates the filter object.
2. Initialization — init(): Called once to initialize the filter and 
prepare resources.
3. Request processing — doFilter(): Called for each matching request. 
The filter can inspect or modify the request, perform checks, and decide 
whether to continue processing.
4. Pass request — chain.doFilter(): Passes the request to the next filter 
or servlet. After downstream processing returns, the filter can process the 
response.
5. Destruction — destroy(): Called when the container removes the filter, 
allowing it to release resources.



Lifecycle flow

Filter created
        |
init() — initialize once
        | 
doFilter() — process each matching request
        |
chain.doFilter() — continue the request
        |
Response returns through the filter chain
        |
destroy() — release resources


Remember: init() is called once per filter instance, 
doFilter() is called for each matching request, and destroy() is 
called when the filter is taken out of service. The container controls 
the lifecycle.

Content is the data sent by the server to the client in response to a request. 
It can be plain text, HTML, JSON, or other formats.

Important methods:

A cache stores copies of responses or resources so they can be reused,

In Servlets, caching can be controlled using HTTP response headers.

In Spring MVC, interceptors are used to perform actions before and after a 
request is handled by a controller.


How interceptors work

1. Client sends a request
Browser → Spring MVC

2. preHandle()
Runs before the controller

3. Controller executes
Processes the request

4. postHandle()
Runs after the controller, before the view renders

5. afterCompletion()
Runs after request processing is complete



The three important methods

Method            	Purpose

preHandle()     	Executes before the controller. Can allow or block the 
                        request.
postHandle()    	Executes after the controller but before the view is 
                        rendered.
afterCompletion()	Executes after request processing finishes, typically 
                        for cleanup or logging.



Where are interceptors useful?

- Authentication checks: Check whether a user is logged in.
- Logging: Record incoming requests.
- Execution time: Measure how long a request takes.
- Request validation: Check certain request conditions before controller 
execution.


Remember: An interceptor works around the controller's request handling, 
while a filter works at the servlet level and can run before the 
request reaches Spring MVC.

----------------------------------------------------------------------------

Difference between Filter and Interceptor 

1. Definition: A Filter processes requests and responses at the Servlet level, 
whereas an Interceptor works with Spring MVC request handling.

2. Execution: A Filter runs before the request reaches the Spring MVC 
DispatcherServlet (depending on its mapping), while an Interceptor runs 
before the controller executes.

3. Framework: A Filter belongs to the Java Servlet API, whereas an Interceptor 
belongs to Spring MVC.

4. Controller access: A Filter does not directly know which controller method 
will handle the request, whereas an Interceptor can access the selected handler.

5. Methods: A Filter uses doFilter(), whereas an Interceptor uses 
preHandle(), postHandle(), and afterCompletion().

6. Purpose: Filters are commonly used for CORS, request/response wrapping, 
and general request processing, whereas Interceptors are used for 
controller-related logging and request checks.

7. Execution after processing: A Filter can perform work after the filter 
chain returns, whereas an Interceptor provides specific callbacks before 
and after controller execution and after request completion.

8. Dependency: Filters can work independently of Spring MVC, whereas 
Interceptors are designed to integrate with Spring MVC.

Point-wise flow of Spring MVC

1. Client: Sends an HTTP request, for example, POST /api/students 
with student data.

2. Tomcat Server: Receives the HTTP request and passes it through 
the configured filter chain.

3. Filter Chain: Filters process the request for tasks such as checking 
headers or handling CORS, then pass it onward.

4. DispatcherServlet: Receives the request and coordinates its processing 
in Spring MVC.

5. HandlerMapping: Identifies the controller method that matches 
the request URL and HTTP method.

6. Interceptor — preHandle(): Runs before the controller and can 
check the request or stop it from proceeding.

7. HandlerAdapter: Invokes the selected controller handler.

8. StudentController — createStudent(): Handles the request and 
calls the service layer.

9. Service Layer: Applies the application's business logic and calls 
the repository.

10. Repository Layer: Performs database operations, such as saving a student.

11. Database: Stores the student data and returns the operation's result.

12. Controller returns the result: The result travels back through the 
service and controller layers.

13. Interceptor — postHandle(): Runs after the handler returns but 
before view rendering, when applicable.

14. Response processing: Spring MVC prepares the response, such as 
JSON for a REST API or a rendered JSP page.

15. Interceptor — afterCompletion(): Runs after request processing 
finishes, typically for logging or cleanup.

16. Filter Chain: Completes any remaining filter processing as the 
response returns.

17. Tomcat Server: Sends the HTTP response back to the client.

18. Client: Receives the response, such as a success message or the 
created student's details.

Remember: HandlerMapping finds the handler, HandlerAdapter invokes it, 
and HandlerInterceptor runs callbacks around handler execution.

Spring AOP (Aspect-Oriented Programming) is a feature in Spring that 
helps us handle common tasks like logging, security, and performance 
monitoring without repeating the same code in every method.



Important terms in Spring AOP

Term	           Simple meaning
Aspect	         A class containing common functionality, such as logging.
Advice	         The code that should execute, and when it should execute.
Pointcut         A rule that selects which methods should be intercepted.
Join point	     A point during program execution where advice can apply. 
                 In Spring's proxy-based AOP, this is typically a method execution.
Target object	   The actual object containing the business logic.

Types of advice

- @Before — Runs before the selected method.

- @After — Runs after the method finishes, whether normally or exceptionally.

- @AfterReturning — Runs when the method completes successfully.

- @AfterThrowing — Runs when the method throws an exception.

- @Around — Wraps the method execution, allowing code to run before and 
after it, or even control whether it proceeds.

@Retention is a Java meta-annotation that specifies how long an annotation 
should be retained.

It determines whether an annotation is available only in source code, 
in the compiled .class file, or at runtime.





Types of @Retention

There are three retention policies.



1. RetentionPolicy.SOURCE

The annotation is available only in the source code and is discarded 
by the compiler when compiling the code.

@Retention(RetentionPolicy.SOURCE)
public @interface MyAnnotation {
}

Example use: @Override is a source-retained annotation.



2. RetentionPolicy.CLASS

The annotation is stored in the compiled .class file, but it is not 
required to be available through runtime reflection. 
This is the default retention policy if you don't specify @Retention.

@Retention(RetentionPolicy.CLASS)
public @interface MyAnnotation {
}




3. RetentionPolicy.RUNTIME

The annotation is stored in the .class file and remains available at runtime. 
Java reflection can read it while the program is running.

@Retention(RetentionPolicy.RUNTIME)
public @interface MyAnnotation {
}



This is especially useful when creating custom annotations for Spring 
or Spring AOP.



Policy	   Source code	  Compiled class	 Available through reflection at runtime
SOURCE	   Yes	        No	             No
CLASS	      Yes	        Yes	             No
RUNTIME	   Yes	        Yes	             Yes





@Documented is a Java meta-annotation that tells Java to include your 
custom annotation in the generated API documentation, usually created using 
Javadoc.

Spring Bean Lifecycle — Step by Step


1. Read bean definition
Spring reads the bean definitions from configuration sources 
such as @Component, @Bean, and configuration classes. 
It learns which objects need to be created and how their dependencies 
should be provided.



2. Instantiate the object
Spring creates the bean object by calling its constructor.
@Service
public class StudentService {
    public StudentService() {
        System.out.println("Constructor called");
    }
}



3. Inject dependencies
Spring injects the required dependencies into the bean, usually through 
constructor injection, setter injection, or field injection.



4. Bean-aware callbacks
If the bean implements Spring's aware interfaces, Spring calls the 
relevant methods. For example, BeanNameAware lets the bean receive its name, 
and ApplicationContextAware lets it receive the application context.



5. Run BeanPostProcessor before initialization
Spring calls the postProcessBeforeInitialization() method of registered 
BeanPostProcessor implementations.

This allows Spring or custom code to inspect or modify the bean before 
its initialization callbacks run. For example, certain annotation-processing 
logic takes place during this stage.

@Override
public Object postProcessBeforeInitialization(
        Object bean, String beanName) {
    System.out.println("Before initialization: " + beanName);
    return bean;
}




6. Run initialization callbacks
Spring invokes the bean's initialization methods, if configured. 
Common examples include:

- Methods annotated with @PostConstruct
- The afterPropertiesSet() method from InitializingBean
- A custom initialization method configured through @Bean(initMethod = "...")

These methods are useful for performing setup after dependencies have been 
injected.



7. Run BeanPostProcessor after initialization
Spring calls the postProcessAfterInitialization() method of registered 
BeanPostProcessor implementations.

This allows further processing after initialization. Spring AOP commonly 
creates or returns a proxy for a bean during this stage, when the bean 
needs to be advised. The proxy may become the object reference that other 
beans use.

@Override
public Object postProcessAfterInitialization(
        Object bean, String beanName) {
    System.out.println("After initialization: " + beanName);
    return bean;
}


Both methods must return an object. Returning null stops further 
BeanPostProcessor processing for that bean.




8. Store the final bean reference
Spring completes bean creation and makes the final bean reference available 
in the application context. This may be the original object or a proxy 
wrapping it.

For example, if StudentService has AOP advice applied, another bean may 
receive a proxy rather than the raw StudentService object.


Complete lifecycle order

1 Read bean definition

2 Instantiate object

3 Inject dependencies

4 Bean-aware callbacks

5 BeanPostProcessor — before initialization

6 Initialization callbacks (@PostConstruct, etc.)

7 BeanPostProcessor — after initialization

8 Register/expose final bean reference

                                    JDBC
                         JAVA DATABASE CONNECTIVITY 

It is a Java API that allows Java applications to connect to databases, execute 
SQL queries, insert, update, delete and retrieve data.




JDBC drivers are software components that allow a Java application to 
communicate with a database through JDBC (Java Database Connectivity).

Different databases use different communication protocols, so a suitable 
JDBC driver translates JDBC calls into commands that the database can understand.


Types of JDBC Drivers

There are four types of JDBC drivers.



1. Type 1: JDBC-ODBC Bridge Driver

This driver converts JDBC calls into ODBC (Open Database Connectivity) calls, 
which are then used to communicate with the database.

Working: Java Application → JDBC → JDBC-ODBC Bridge → ODBC Driver → Database

Disadvantages: It requires an ODBC driver and is platform-dependent. 
The JDBC-ODBC Bridge was removed from the JDK in Java 8, so it is not used in 
modern Java applications.



2. Type 2: Native-API Driver

This driver converts JDBC calls into database-specific native API calls. 
It requires native database client libraries to be installed on the user's 
system.

Working: Java Application → JDBC Driver → Native Database Library → Database

Disadvantages: It depends on platform-specific native libraries and requires 
additional installation.



3. Type 3: Network Protocol Driver

This driver sends JDBC calls to a middleware server, which translates them 
into the database-specific protocol and communicates with the database.

Working: Java Application → JDBC Driver → Middleware Server → Database

Advantages: It can support multiple database types through middleware and does not require native database libraries on every client.

Disadvantages: It requires a middleware server, which adds complexity and may 
introduce network overhead.




4. Type 4: Thin Driver (Pure Java Driver)

This driver converts JDBC calls directly into the database's native network 
protocol. It is written entirely in Java and communicates directly with the 
database server.

Working: Java Application → Type 4 JDBC Driver → Database

Advantages: It is platform-independent, does not require native libraries, and is commonly used in modern Java applications.

Examples: MySQL Connector/J for MySQL and pgJDBC for PostgreSQL.



Comparison of JDBC Drivers

Type	      Name	              Native library required?	      Communication
Type 1	   JDBC-ODBC Bridge	  ODBC driver required	         Through ODBC
Type 2	   Native-API	        Yes	                           Through native API
Type 3	   Network Protocol	  Not on each client	            Through middleware
Type 4	   Thin Driver	        No	                           Directly with database

JDBC Methods: 


1. executeQuery()
executeQuery() is a method of the JDBC Statement interface used to execute 
SQL queries that retrieve data from a database.

It is mainly used with the SELECT statement. It returns a ResultSet object 
containing the records retrieved from the database. The returned records can 
then be accessed one by one.

Example use: Fetching all student records from a database.



2. executeUpdate()
executeUpdate() is a method of the JDBC Statement interface used to 
execute SQL statements that modify database records or change the database 
structure.

It is commonly used with INSERT, UPDATE, and DELETE statements. 
It can also execute DDL statements such as CREATE TABLE. For DML statements, 
it returns an integer representing the number of affected rows; for 
DDL statements, it returns 0.

Example use: Inserting a new student or updating a student's age.



3. execute()
execute() is a method of the JDBC Statement interface used to execute SQL 
statements when the type of result may vary.

It can execute different types of SQL statements. It returns a boolean value: 
true if the first result is a ResultSet, or false if the first result is an 
update count or there is no result.

Example use: Executing a SQL statement when the application needs to determine 
whether the result is a result set or an update count.

Spring JDBC is a module of the Spring Framework that simplifies database 
operations in Java applications. It is built on top of standard JDBC and 
reduces the amount of repetitive code required to connect to a database, 
execute SQL queries, process results, and handle exceptions.

In traditional JDBC, developers must manually manage connections, statements, 
result sets, and exception handling. Spring JDBC handles much of this 
repetitive work, allowing developers to focus on writing SQL queries and 
application logic.


The main purpose of Spring JDBC is to make database access easier and reduce 
boilerplate code.


Its major advantages include:

1. Less code: Reduces repetitive JDBC operations.

2. Exception handling: Converts JDBC's checked SQL exceptions into Spring's 
unchecked DataAccessException hierarchy.

3. Resource management: Automatically manages resources such as connections 
and statements.

4. Easy query execution: Provides convenient methods for executing SQL queries.

5. Integration with Spring: Works with dependency injection and Spring 
transaction management.



JdbcTemplate is the main class commonly used in Spring JDBC. 
It executes SQL statements and handles resource management and exception 
translation.

The Template Method Design Pattern is a behavioral design pattern that defines 
the basic steps of an algorithm in a parent class while allowing child classes 
to implement or customize certain steps.

In simple words, the parent class decides what steps should be performed and 
in what order, while child classes decide how some of those steps are performed.


The parent class defines the sequence of steps. Child classes provide their own 
implementations for the steps that vary.

A DataSource is a Java interface used to obtain connections to a database. 
It acts as a source of database connections for an application.

Instead of creating database connections manually every time using 
DriverManager, an application can use a DataSource to obtain and manage 
connections more efficiently.

In Spring JDBC, DataSource provides the database connections that JdbcTemplate 
uses to execute SQL queries.

----------------------------------------------------------------------------

Types of DataSource

Common implementations include:

1. DriverManagerDataSource: Creates a new database connection whenever a 
connection is requested. It is useful for simple examples and testing, but 
it does not provide connection pooling.

2. HikariDataSource: Provides connection pooling, allowing connections to be 
reused instead of repeatedly creating new ones. HikariCP is commonly used by 
Spring Boot applications.

3. BasicDataSource: Apache Commons DBCP provides this implementation, which 
supports connection pooling and database connection configuration.

----------------------------------------------------------------------------

Connection pooling is a technique in which a collection of database connections 
is created and maintained so that an application can reuse them whenever needed.

Normally, establishing a database connection takes time and resources. 
If an application creates a new connection for every database operation, 
it can reduce performance. Connection pooling solves this problem by reusing 
existing connections instead of creating a new one every time.

In Spring Boot, HikariCP is the default connection pool implementation in a 
typical JDBC setup.

JDBC template 


1. update()
The update() method is used to execute SQL statements that modify database data,
 such as INSERT, UPDATE, and DELETE.

It returns an integer representing the number of rows affected by the 
operation.

Example uses:
- Inserting a new student into the database.
- Updating a student's age.
- Deleting a student record.

Return type: int



2. query()
The query() method is used to retrieve multiple rows from a database. 
It executes a SELECT query and converts the returned rows into Java objects 
or another required format, usually using a RowMapper.

Example uses:
- Fetching all students from the database.
- Retrieving all students whose age is greater than 18.
- Getting a list of student names.

Return type: Often List<T> when used with a RowMapper.
If no records match, it normally returns an empty list.





3. queryForObject()
The queryForObject() method is used when a query is expected to return 
exactly one result, such as a single value or one row mapped to a Java object.

Example uses:
- Finding the total number of students.
- Fetching a student's name using their ID.
- Retrieving one student record by ID.

Return type: Depends on the query and mapping, such as Integer, String, or Student.

If the query returns no rows, Spring generally throws an 
EmptyResultDataAccessException. If a single-result query returns multiple rows, 
it generally throws an exception as well.

It describes how one row of database data should be converted into a Java object.

The mapRow() method receives two parameters:
- ResultSet: Contains the data retrieved from the database. It allows us to access column values.

Hibernate in Java

Hibernate is an ORM (Object-Relational Mapping) framework for Java that 
simplifies the process of storing, retrieving, updating, and deleting data 
in a relational database.

Instead of writing SQL queries for every database operation, developers 
can work with Java objects, and Hibernate generates or executes the 
required SQL queries.

Hibernate is commonly used with Spring Boot applications to interact with 
databases such as MySQL and PostgreSQL.

EntityManager in JPA
EntityManager is an interface in JPA (Jakarta Persistence API) used to manage 
entity objects and perform database operations such as inserting, retrieving, 
updating, and deleting records.

It acts as a bridge between Java entity objects and the persistence context, 
which keeps track of the entities being managed.



Persistence Context in JPA
Persistence Context is an environment in JPA that manages entity objects 
during their lifecycle. It keeps track of entity objects and their changes 
so that these changes can be synchronized with the database.

In simple words, the persistence context acts like a temporary working area 
for entity objects. It remembers which objects are being managed and detects 
changes made to them.

States of an Entity

An entity can have the following states in relation to a persistence context.

State                     	Meaning
Transient       	          The object is created in Java but is not managed by a persistence context.
Managed (Persistent)	      The object is associated with a persistence context, and changes to it can be tracked.
Detached	                  The object was previously managed but is no longer associated with the persistence context.
Removed	                    The managed entity is marked for deletion from the database.




Important Points

1. An EntityManager manages entities through a persistence context.

2. The persistence context maintains one managed entity instance for a given entity type and primary key within that context.

3. It tracks changes to managed entities through dirty checking.

4. It can reduce repeated database retrievals by returning an already managed entity when appropriate.

5. Changes are synchronized with the database during flushing, but the actual transaction commit is a separate step.

6. The persistence context is not the database itself; it manages entity state in memory.

@Table Annotation in JPA
@Table is an annotation in JPA used to specify the database table associated 
with an entity class.

By default, JPA maps an entity class to a table using its entity name or the 
configured naming strategy. We use @Table when we want to specify the table 
name or configure other table-related details.




@Column Annotation in JPA
@Column is an annotation in JPA used to specify the mapping between a Java 
entity field and a database table column.

It allows us to customize the column name and define properties such as 
nullability, uniqueness, length, and whether the column is updatable.





@Enumerated Annotation in JPA
@Enumerated is a JPA annotation used to specify how an enum value in a Java 
entity should be stored in a database.

An enum is a Java data type that represents a fixed set of constants, such as 
student status, order status, or user roles.





@Lob Annotation in JPA
@Lob stands for Large Object. It is a JPA annotation used to map a Java field 
to a database column capable of storing large amounts of data, such as lengthy 
text or binary content.

It is commonly used to store descriptions, documents, images, audio, 
or other large data, depending on the database and mapping configuration.

1. Types of LOB

There are two main types of Large Objects.


1. CLOB (Character Large Object)
Used for large character-based data, such as lengthy text, articles, or 
descriptions.

In JPA, a String field annotated with @Lob is typically mapped to a character 
large-object type.



2. BLOB (Binary Large Object)
Used for large binary data, such as image files, PDFs, audio, or other binary 
content.

In JPA, a byte[] field annotated with @Lob is typically mapped to a binary 
large-object type.

@Transient is a JPA annotation used to specify that a field of an entity

In simple words, the field exists in the Java object, but JPA ignores it when

@Embeddable and @Embedded Annotations in JPA
@Embeddable and @Embedded are JPA annotations used to represent a group of 
related fields as a reusable component inside an entity.

They allow us to organize entity classes without creating a separate database 
table for the embedded object.


1. @Embeddable
@Embeddable is used on a Java class whose fields can be embedded into another 
entity.

The class does not have its own table merely because it is marked @Embeddable. 
Its fields are mapped as part of the owning entity's table.


2. @Embedded
@Embedded is used in an entity class to include an object of an @Embeddable 
class.

It tells JPA that the object's fields should be mapped as columns in the owning 
entity's table.





@AttributeOverride in JPA
@AttributeOverride is a JPA annotation used to change the column mapping of a 
field inherited from or defined in an @Embeddable class when that field is used 
inside an entity.

In simple words, it allows us to override the default database column name 
of an embedded object's field without changing the original embeddable class.






@ElementCollection in JPA
@ElementCollection is a JPA annotation used to store a collection of basic 
values or embeddable objects that belong to an entity, without creating a 
separate entity class for each value.

It is commonly used when one entity has multiple values, such as a student's 
phone numbers, a user's skills, or an employee's email addresses.
